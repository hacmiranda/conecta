Este arquivo orienta o Claude Code (claude.ai/code) no trabalho com o código deste repositório. **Escrito em português do Brasil, como todo o projeto.**

## Projeto

**Conecta CRPRS** - Sistema de gestão de demandas por setor do Conselho Regional de Psicologia do Rio Grande do Sul (CRPRS). Backend em PHP/MySQL e frontend em JavaScript puro (vanilla), sem etapa de build. Originou-se do CRPDESK (helpdesk): cada e-mail recebido na caixa de um setor abre uma demanda naquele setor. Desde 03/11/2026 absorveu o **METRICA360** (pesquisa de satisfação, Meu Painel e Registro de Atividades), que deixou de ser um sistema à parte e virou o módulo **Satisfação** do Conecta (mesmo banco, mesmo login; ver "Unificação com o METRICA360").

Vocabulário: a entidade de banco continua `tickets` (e `ticket_*`), mas na interface e nos textos é **demanda**. Papéis: `admin` (administrador), `coordenador_geral`, `supervisor`, `coordenador`, `gestor`, `operador` e `cliente` (solicitante externo).

## Arquitetura

### Fluxo das requisições
Toda requisição à API passa por `api/middleware/auth.php` (verificação do JWT e controle de acesso por papel). Os controllers ficam em `api/controllers/*.php`. O frontend é uma aplicação de página única em `frontend/index.html`, movida por `frontend/script.js` e pelos arquivos de cada domínio.

### Autenticação
- **Sessão (auditoria fase 2, 26/10/2026):** o JWT fica num **cookie HttpOnly** `conecta_sessao` (`SameSite=Strict`, `Path=/conecta`, `Secure` em HTTPS), gravado por `auth.php`/`auth-sso.php`/`alterar-senha.php` via `AuthMiddleware::definirCookieSessao()`; o JavaScript nunca o vê, então um XSS em outro sistema do mesmo domínio (site, antigo METRICA360) não consegue roubá-lo. O navegador guarda só `cd_usuario` e `cd_csrf_token` no `localStorage`; a resposta do login não traz mais `token`. `getAuthHeaders()`/`setSecurityHeaders()` mandam só o `X-CSRF-Token` (o cookie vai sozinho). `Authorization: Bearer` continua aceito (testes, integrações). Consequência: abrir o sistema num `<iframe>` de **outro site** não manda o cookie (só agregadores do mesmo site funcionam).
- **Login por e-mail ou nome de usuário (16/11/2026):** o campo de login (`login.html` `#login`, "E-mail ou usuário") envia `{login, senha}` (`auth.php` ainda aceita a chave antiga `email`). Com `@` procura `usuarios.email`; sem `@`, `usuarios.username` (`UsuarioService::campoDoLogin`/`normalizarLogin`: sem espaços nas pontas, minúsculas). O nome de usuário nunca tem `@`: `UsuarioService::PADRAO_USERNAME` = `^[a-z0-9._-]{3,50}$`, exigido por `usuarios.php` POST/PUT (400, `lerUsernameInformado`) e por `usuarios.js` (`erroUsernameDigitado`, dica abaixo do campo); editar com o nome de usuário em branco mantém o atual (antes gerava de novo `nome.sobrenome2`). O atraso por conta conta pela conta encontrada (`conta_id<N>`), não pelo texto digitado; `auditoria_login.email` recebe o e-mail da conta, ou `LogService::mascararLogin()` quando não há conta. "Esqueci a senha" continua só por e-mail. Testes: `UsuarioServiceTest`, matriz de acesso [8b]. A matriz escolhe dois setores ativos **sem coordenador** (a seção [9] cria um coordenador de teste neles; desde a importação do METRICA360, Cadastro e Cobrança têm coordenador). Especificação/plano: `docs/superpowers/specs|plans/2026-11-16-login-por-usuario-e-importacao-metrica360*`.
- O token vale **12 h** (`exp`); `verificarAuth()` renova o cookie quando faltam menos de 2 h, mantendo o mesmo `jti` e `csrf`. Token sem `exp` (versões antigas) é recusado (401 `sessao_encerrada`, o frontend vai para o login). `verificarAuth()` relê do banco, a cada requisição, `tipo`, `setor_id`, `ativo`, `token_versao` e `trocar_senha`: mudança de papel/setor e desativação valem na hora.
- Revogação de sessão: "Sair" grava o `jti` do token em `sessoes_revogadas` e apaga o cookie (só aquela sessão termina; linhas com mais de 2 dias são apagadas). Há dois "Sair": no menu do avatar e, **desde 19/11/2026, no rodapé da sidebar** (`#btn-sidebar-sair`, ouvinte em `sidebar-navegacao.js`, chama `fazerLogout()`). "Sair de todos os dispositivos" (menu do avatar; `logout.php` com `{todas: true}`) também soma `token_versao`. Troca/redefinição de senha e desativação somam `usuarios.token_versao` (claim `tv`), encerrando todas as sessões da pessoa.
- `usuarios.trocar_senha = 1` (usuários novos, senha redefinida pelo admin/gestor/coordenador): toda API, menos `alterar-senha.php`/`logout.php`, responde 403 `trocar_senha` até a pessoa trocar; o frontend mostra só "Alterar senha".
- Sete papéis (`usuarios.tipo`, migração 39): `cliente`, `operador`, `gestor`, `coordenador`, `supervisor`, `coordenador_geral`, `admin`. Coordenador, supervisor e coordenador geral: ver "Unificação com o METRICA360" e "Ajustes de papéis, menus e SLA (19/11/2026)". Gestor e operador pertencem a um setor (`usuarios.setor_id`); o admin não tem setor e escolhe um no cabeçalho. `cliente` = solicitante externo criado a partir do e-mail recebido: nunca entra no sistema (login, SSO e recuperação de senha o recusam). Só entra quem foi cadastrado pelo admin, coordenador ou gestor (o SSO não cria usuários). **Promoção (18/11/2026):** o admin transforma um `cliente` em usuário interno pelo botão "Promover a usuário interno" da aba Solicitantes (`usuarios.js` `promoverSolicitante`, delegado `data-acao-usuario="promover"`): papel, setor, nome de usuário, cargo e uma **senha inicial** (o solicitante nunca teve senha), enviados por `usuarios.php` PUT; o servidor só aceita do admin (403 nos demais), exige `senha` válida (400), grava `trocar_senha = 1` e `ativo = 1`, apaga tokens de recuperação e audita `promover_solicitante`; as demandas que ele abriu continuam com ele como solicitante. Matriz [8c].
- Senhas: só hash (`SenhaService`: mín. 10 caracteres, maiúscula, minúscula, número e caractere especial; Argon2id). O login tem limite por IP e por conta (login certo zera só o contador da conta, não o do IP: SEG-06; **pode ser desligado temporariamente desde 16/11/2026** com `LOGIN_LIMITE_TENTATIVAS_LOCAL|_PROD=0` no `.env`, lido por `RateLimitService::limiteDeLoginLigado()`: desliga o 429 por IP, o atraso por conta e, via `login-config.php` `limite_tentativas: false`, a trava de 5 erros da tela de login; chave ausente = ligado; **o `.env` local está com 0 agora**). Atrás de `PROXIES_CONFIAVEIS`, o `X-Forwarded-For` é lido da direita para a esquerda (`RedeService::ipDoEncaminhamento`, SEG-07).
- Desativar um usuário ou movê-lo para outro setor devolve ao setor as demandas abertas dele (`AcessoService::devolverDemandasDoResponsavel`).
- CAPTCHA Turnstile no login (`api/config/turnstile.php`, só em produção). `login.html` pergunta ao público `api/controllers/login-config.php` (`{turnstile, turnstile_site_key}`, mesma regra de `validateTurnstile`: `APP_ENV` de produção + segredo definido) em vez de adivinhar pelo endereço — desde 12/11/2026, para o sistema local aberto pelo IP da rede (ex.: `http://192.168.1.102/conecta/`) entrar sem CAPTCHA (antes só `localhost`/`127.0.0.1` pulavam, e o widget da Cloudflare falhava no IP).
- Toda chamada à API exige a sessão (cookie ou Bearer) e, em POST/PUT/DELETE, o cabeçalho `X-CSRF-Token` (claim `csrf` do JWT). O SSO (`auth-sso.php`) exige `exp` no máximo 5 min depois de `iat`, `jti` de uso único (hash gravado em `sessoes_revogadas`) e, quando definidos no `.env`, `iss`/`aud` (`SSO_ISSUER_*`/`SSO_AUDIENCE_*`).

### Regras de acesso (setores)
- `api/services/acesso-service.php` (`AcessoService`) é o único lugar que decide quem vê/opera uma demanda: admin = todas; gestor = as do próprio setor; coordenador = as dos setores dele; operador = aquelas em que é o responsável (ou que abriu). Use sempre ele; nunca filtre por papel por conta própria.
- **Fila do setor (17/11/2026):** o operador também vê as demandas abertas do SETOR DELE **sem responsável** (`AcessoService::naFilaDoSetor`: lista `tickets.php?escopo=abertas` e detalhe, só leitura por `podeLerTicket`; `podeVerTicket`/`podeOperarTicket` não mudaram, então ele não altera nem comenta antes de assumir) e pega uma com `demanda-acoes.php` `acao=assumir` (`podeAssumirTicket`: operador da fila, ou gestor/coordenador do setor como atalho; sem comentário; linha travada, o segundo clique recebe 409; mesmos efeitos de atribuir a si mesmo, histórico `assumiu`, a gestão do setor é avisada, sem o e-mail "atribuída para você" para ele mesmo). O detalhe devolve `fila_do_setor`/`pode_assumir`; `detalhe-demanda.js` mostra a faixa "fila do setor" e o botão "🙋 Assumir demanda" (delegado `data-acao-demanda="assumir"`); no Kanban o operador só arrasta/muda o status dos próprios cartões. O gestor continua distribuindo. Matriz [2b].
- Três níveis: `podeVerTicket` (participação atual), `podeOperarTicket` (alterar) e `podeLerTicket` (soma o histórico: gestor de um setor por onde a demanda passou, operador que já a atendeu). Quem lê pelo histórico recebe `acesso_historico`/`somente_leitura` e a tela fica só de leitura.
- Lixeira: todo perfil que pode operar uma demanda a envia para a lixeira (`DELETE tickets.php?id=`, `tickets.excluido_em`); só o admin a vê (`?escopo=lixeira`), restaura (`PUT ?acao=restaurar`) ou exclui de vez (`DELETE ?definitivo=1`, apaga os arquivos). Toda lista/relatório/dashboard filtra `excluido_em IS NULL`.
- Status e prioridade são conferidos no servidor contra o catálogo **e** a ativação do setor (`CatalogoService`); `tickets.status` é um VARCHAR livre. `CatalogoService::STATUS_ESSENCIAIS` (`novo`, `nova_resposta`, `reaberto`, `encerrado`: o sistema os aplica sozinho) são sempre permitidos e não podem ser desligados na Ativação por Setor (`setor-config.php` responde 400; a tela mostra o interruptor travado). **A aba Prioridades da Ativação por Setor é só do administrador desde 19/11/2026** (some para os demais; `setor-config.php` responde 403 em `tipo=prioridades` para quem não é admin). Na transferência para outro setor, status/prioridade inativos lá viram `novo`/`normal` (ou a primeira prioridade ativa), com histórico.
- `AcessoService::setorEscopo($user)` (um setor só, telas de configuração) e `AcessoService::escopoSetores($user)` (listas e indicadores): o admin e a visão total podem mandar `?setor_id=` (vazio = todos os setores); o coordenador só entre os setores dele (fora deles: 403); os demais ficam presos ao próprio setor, qualquer que seja o parâmetro.
- As ações de fluxo (encaminhar, devolver, repassar, transferir de setor) passam por `api/controllers/demanda-acoes.php` e exigem comentário.
- A linha do tempo da demanda é montada por `api/services/timeline-service.php` (comentários + `ticket_historico`); as passagens por setor/responsável ficam em `ticket_setor_log` / `ticket_agente_log`.

### Estrutura do backend
- `api/config/` — detecção do ambiente, conexão com o banco (PDO), configuração de e-mail
- `api/controllers/` — um arquivo PHP por recurso/funcionalidade (~50 endpoints)
- `api/middleware/auth.php` — validação do JWT, conferência de papéis, CSRF, trava de escrita dos perfis de consulta
- `api/services/` — regras de negócio: regras de acesso, linha do tempo, cálculo do SLA, envio de e-mail, auditoria, criptografia das senhas das caixas, log único em arquivo (`LogService`, `backend/logs/<canal>-AAAA-MM-DD.log`, um arquivo por dia guardado por `LOG_RETENCAO_DIAS` dias; `LogService::detalhe()` só com `LOG_DETALHADO=1`; os testes gravam na pasta temporária), cache curto em arquivo (`CacheArquivoService`, `backend/cache/<grupo>/`)
- `api/cron/` — tarefas agendadas de leitura de e-mail, lembretes, fila de e-mail e pesquisas

Fuso horário: PHP `America/Sao_Paulo` e sessão MySQL `-03:00` (definido em `Database::getConnection()`), então `NOW()` e `date()` concordam.

O ambiente vem de `APP_ENV` em `api/config/.env` (`local` | `production`; ausente = production) — nunca do cabeçalho Host. Credenciais e chaves vêm só de `api/config/.env` (`*_LOCAL` / `*_PROD`); ver `.env.example` (banco, IMAP/SMTP, JWT/CSRF, CORS, SSO, `SETOR_EMAIL_ENCRYPTION_KEY_*`, `INTEGRATION_API_KEY_*`).

### Estrutura do frontend
Um único HTML (`frontend/index.html`), sem roteador de framework e sem build. Tags `<script>` clássicas (sem módulos ES): toda função/variável é global e os atributos `onclick="..."` as chamam pelo nome. **A ordem de carga no `index.html` importa** quando dois arquivos declaram a mesma função (vale a última — ex.: `ajuda.js` vem antes de `tutorial.js` de propósito). **Todo arquivo alterado ganha um `?v=` novo.**

O `script.js` foi dividido por domínio em 12 ondas (Fase 12/P1, concluída em 22/10/2026; planos em `docs/superpowers/plans/2026-10-2*-frontend-divisao-script-onda*.md`, especificação em `docs/superpowers/specs/2026-10-15-frontend-api-e-divisao-script-design.md`). Passou de ~10.000 para ~2.200 linhas (1.600 em 03/11/2026).

### Principais tabelas
- `tickets` — entidade central (a "demanda"); `descricao` é LONGTEXT (HTML rico, pode ter imagens em base64), `descricao_texto` é o texto puro para busca/resumo da lista (preencher em todo INSERT/UPDATE de `descricao`); liga-se a `usuarios`, `categorias`, `setores` (`setor_id`) e ao responsável (`agente_id`)
- `setores` — setores; `setor_coordenacao` (migração 42: setor onde só trabalha o coordenador, fora do seletor do cabeçalho e do Cruzamento), `pesquisa_painel` (aparece no Painel de Setores da Satisfação); `setor_emails` (uma caixa por setor: recebe por IMAP e envia por SMTP, senhas cifradas), `setor_status` / `setor_prioridades` (ativação, por setor, do catálogo global)
- `ticket_status` / `ticket_prioridades` — catálogo global; `ticket_status.congela_sla` (o status pausa o SLA) e `ticket_prioridades.sem_sla` (migração 42: a prioridade não tem SLA, ex.: `baixissima`)
- `usuarios`, `usuario_setores` (setores adicionais do coordenador, migração 39)
- `categorias` / `macrocategorias` — pertencem a um setor (`setor_id`). Na interface, `macrocategorias` = "Categoria" e `categorias` = "Subcategoria". O nome da categoria é único por setor; o da subcategoria é único **por categoria** (migração 24: a mesma "Inscrição" pode existir em "Pessoa Física" e "Pessoa Jurídica"). Onde a subcategoria aparece sozinha (listas, seletores, relatórios, dashboard, histórico) o rótulo é `"Subcategoria - Categoria"`: SQL `CONCAT_WS(' - ', c.nome, mc.nome)` (`tickets.php` `categoria_nome`, `relatorios.php`, `dashboard.php`, histórico em `tickets.php`/`demanda-acoes.php`), `categorias.php` GET devolve como `rotulo`, função `rotuloSubcategoria(cat)` em `categorias.js`
- `horarios_uteis` + `feriados` — expediente e feriados **por setor** (o SLA da demanda usa o do setor dela)
- `comentarios` — comentários; `comentario` é LONGTEXT (aceita imagens em base64 do Quill); `interno` (migração 23) marca a nota interna, que nunca vai ao solicitante
- `ticket_historico` — eventos da linha do tempo (status, prioridade, categoria, atribuição, transferência de setor, abertura...); as mesclagens também ficam aqui (`acao = merge`); a tabela antiga `historico` saiu na migração 21
- `ticket_setor_log` / `ticket_agente_log` — janelas de passagem por setor/responsável; fechadas ao encerrar/cancelar
- `ticket_sla` — tempos de SLA da demanda (`primeira_resposta_em`, `resolvido_em`, `pausado_em`, `tempo_pausado_segundos` etc.)

### Conteúdo não confiável (XSS)
- Backend: HTML rico (descrição, comentários, macros, integração) passa por `HtmlSanitizer::rico()` (HTML Purifier, `api/services/html-sanitizer.php`); campos de texto puro (títulos, nomes, texto de lembrete) por `HtmlSanitizer::texto()` (desde 01/11/2026 tira só tags de verdade, repetidamente, e põe um espaço depois de um `<` que abre uma tag sem fechar; o `strip_tags` apagava tudo depois de um `<` solto: BUG-01). O corpo do e-mail recebido é gravado escapado (`htmlspecialchars` + `nl2br`).
- Frontend: todo valor da API inserido com `innerHTML` passa por `sanitizeHTML()` (texto) ou `htmlSeguro()` (HTML rico, pelo `frontend/lib/purify.min.js` local); textos dentro de `onclick` usam `argJs()` + `decodeURIComponent`.

### Criptografia do SMTP global (corrigido em 23/10/2026)
O servidor/porta do remetente global caem em `smtp.gmail.com:587` (STARTTLS) se `SMTP_HOST_*`/`SMTP_PORT_*` não estiverem no `.env` — mas `email-sender.php` e `testar-email.php` fixavam `SMTPSecure = ENCRYPTION_SMTPS` (TLS implícito, porta 465) qualquer que fosse a porta, então o SMTP sempre falhava num servidor STARTTLS (o IMAP funcionava, por não depender disso). `EmailConfig::segurancaSmtp()` agora escolhe `'tls'`/`'ssl'` a partir de `SMTP_SEGURANCA_*` (opcional) ou pela porta (587 → STARTTLS; outra → SSL implícito) — a mesma convenção já usada por setor (`setor_emails.seguranca`). Os dois arquivos chamam essa função em vez de fixar `ENCRYPTION_SMTPS`.

### Lista de demandas (paginação no servidor)

### Regras do e-mail recebido
Demandas vindas de e-mail são criadas **só quando o cron `api/cron/verificar-emails.php` roda** (produção: cron-job.org a cada 2 min por HTTP + `X-Cron-Key`). No ambiente local nada o agenda — rode à mão (`php api/cron/verificar-emails.php`), senão a demanda "nunca abre". Os assuntos são decodificados com `iconv_mime_decode` (`EmailService::decodificarTexto`); o `mb_decode_mimeheader` deixava `_` no lugar dos espaços em assuntos Q-encoded (corrigido em 23/10/2026). Corpo e anexos são lidos pelo `EmailMime` (ver auditoria fase 5). A mesma mensagem entregue a duas caixas de setor abre uma demanda em cada setor (a duplicidade é conferida por caixa).

A resposta com o protocolo (`#CRPRS2026-0001`) no assunto só vira comentário se o remetente for o solicitante, alguém que recebeu cópia (`ticket_copias`) ou a equipe do setor, e se o setor da caixa for um por onde a demanda passou; senão abre demanda nova. E-mails das próprias caixas do sistema e respostas automáticas são ignorados (`emails_processados.tipo = 'ignorado'`), assim como os que batem com os **filtros de e-mail** de um setor (ver "Filtros de e-mail por setor"; só para o que abriria demanda nova). Falhas são refeitas (`emails_erro`) até 5 vezes, em vez de se perderem. Desde a auditoria de 01/11/2026 (BUG-08/DES-01): cada mensagem e cada caixa ficam protegidas por `catch (Throwable)`; a tentativa é contada em `emails_erro` **antes** do processamento (texto `EmailService::MARCA_INTERROMPIDA`), então um erro fatal (memória, tempo) também conta e a mensagem é descartada depois de 5; `verificar-emails.php` tem um `register_shutdown_function` que ainda roda os lembretes e a fila depois de um erro fatal; anexos de extensão proibida ou acima de 20 MB (estimados pelo `bytes` da estrutura) são recusados **sem baixar** (`EmailMime::anexos(..., $recusarAntes)`); só mensagens novas são lidas: os UIDs já tratados ficam guardados por caixa em `backend/cache/email-uids/caixa-<id>.json` (valem enquanto o UIDVALIDITY for o mesmo; apagar a pasta é seguro) e o resto é conferido com um `imap_fetch_overview` + uma consulta ao banco; `verificar-emails-perdidos.php` ignora essa memória. Mensagens já processadas não são mais marcadas como lidas de novo. Uma linha de resumo por caixa no log.

### Protocolo único (`#CRPRS2026-0001`, 23/10/2026)
Toda demanda ganha um protocolo ao ser criada, mostrado em todo lugar no lugar do id interno (`tickets.id` continua sendo a chave primária/estrangeira/referência de URL — o protocolo é só a identidade exibida). Formato `CRPRS<ano>-<sequência de 4 dígitos>` (passa de 4 dígitos sozinho), gravado sem `#` em `tickets.protocolo` (`VARCHAR(20) NULL UNIQUE`; nulo só em linhas anteriores à migração ou em inserções diretas de teste, ex.: `api/tests/matriz-de-acesso.php`). `ProtocoloService` (`api/services/protocolo-service.php`):
- `gerar($db)` — chamar **antes** do `INSERT INTO tickets` (não usa o id da demanda). Contador atômico por ano em `protocolo_sequencia` (`ano` PK, `ultimo`) via `INSERT ... ON DUPLICATE KEY UPDATE ultimo = LAST_INSERT_ID(ultimo + 1)` — sem a corrida do `MAX()+1`; conferido com 50 processos PHP simultâneos de verdade (nenhuma colisão). Recomeça sozinho em 1º de janeiro (nova linha de `ano`).
- `rotulo($protocolo, $id)` / `rotuloPorId($db, $id)` (com cache por requisição) — `"#" + protocolo`, caindo para `"#" + id com zeros` só quando não há protocolo (linhas antigas/de teste).
- `extrair($assunto)` — lê o protocolo do assunto do e-mail (`#CRPRS2026-0001`, com/sem colchetes, sem diferenciar maiúsculas, espaços a mais). **O formato antigo de 5 dígitos (`#00123`) não é mais reconhecido** (o sistema não estava em produção quando o protocolo entrou); `EmailService::extrairTicketId()` e `EmailSender::detectarContexto()` usam essa função.
- O protocolo **nunca muda**: transferência, reabertura (pela tela ou por e-mail) e mesclagem mantêm o protocolo de cada demanda (o histórico/comentários da mesclagem citam os dois protocolos pelo rótulo, não pelo id).
- Frontend: `numeroDemanda(obj)` em `script.js` — aceita um objeto de demanda (`protocolo`/`ticket_protocolo`/`id`/`ticket_id`/`registro_id`) ou só o id e sempre devolve `"#..."`. Toda lista/detalhe/relatório/auditoria usa essa função no lugar de `padStart(5,'0')`. A busca de demandas também casa `t.protocolo LIKE`. Endpoints que só expunham `ticket_id` (`auditoria.php`, `auditoria-avancada.php`, `email-logs.php`, `emails-processados.php`) agora devolvem também `ticket_protocolo` via `LEFT JOIN tickets`.
- `backend/email-template*.html` mantêm o `#` literal antes de `{{NUMERO_TICKET}}`; o código passa o protocolo **sem** `#` nesse marcador (`ltrim($rotulo, '#')`) e o rótulo completo com `#` nos assuntos e nos corpos em texto puro.
- Integração (`api/controllers/integracoes/abrir_chamado.php`): a resposta inclui `"protocolo": "#CRPRS2026-0045"` — os sistemas satélites devem mostrar isso ao cidadão, não o `ticket_id` (`docs/especificacoes/PROMPT_INTEGRACAO_SISTEMA_SATELITE.md` atualizado).

Ligar começa no início do período do calendário de hoje (ou no dia seguinte ao fim da última vigência). Desligar ou trocar a periodicidade fecha a atual no **fim do período corrente** (semana seg–dom, mês 1º ao último dia) e, na troca, a nova começa no dia seguinte. Os períodos são os **do calendário recortados pela vigência**: o primeiro e o último podem ser parciais, identificados pela data de início do período do calendário (`data_referencia`, que num período parcial cai antes da vigência) e cobrados ao fim do período recortado. `PrazoAtividadeService::resolverPeriodoDoSetor` resolve a data pedida (o tipo `semana`/`mes` desempata a mesma `data_referencia`).

### Tempo trabalhado na demanda (17/11/2026)

### SLA
`api/services/sla-service.php` calcula segundos úteis com o expediente (`horarios_uteis`) e os feriados (`feriados`) do setor da demanda (setor sem expediente cai no "Geral"). **O SLA fica pausado** quando o status congela (`ticket_status.congela_sla`) **ou** quando a prioridade não tem SLA (`ticket_prioridades.sem_sla`, desde 19/11/2026: "Baixíssima (Sem SLA)"); regra única em `SLAService::pausaSla($status, $prioridade)` e `DemandaService::ajustarPausaSla()`. `SLAService::situacao()` (Fase 8) é a fonte única da situação do SLA (`{tipo, segundos_restantes, percentual, vencido, pausado}`; `null` na prioridade sem SLA); `tickets.php` a anexa como `ticket['sla']` em toda resposta de lista/detalhe (`anexarSla()`), e o frontend (`status-sla.js`, `demandas.js`) só a desenha — não há conta de horário útil em JS. As médias de primeira resposta e de resolução (`SLAService::mediaPrimeiraResposta()`/`mediaResolucao()`, Dashboard e Relatórios) pulam as demandas na prioridade sem SLA.

## Regras do Projeto (.agent/rules)

### Idioma (IDIOMA_PTBR.md)
- **Todo o projeto usa Português do Brasil (pt-BR)** — respostas, comentários de código, commits e documentação.
- Comentários PHP/JS **obrigatoriamente em português**. Ex: `// Verifica se o usuário existe`.
- Nomes de variáveis/funções: seguir o padrão já existente no arquivo. Código novo independente prefere português.
- Mensagens de commit em português. Ex: `fix: correção no redirecionamento de login`.
- Termos técnicos consagrados (bug, deploy, loop, fetch) podem ser mantidos em inglês quando a tradução prejudica a clareza.

### Backend PHP (BACKEND_PHP.md)
- Todas as respostas da API devem ser JSON com `header('Content-Type: application/json')`.
- Usar códigos HTTP corretos: 200, 201, 400, 401, 403, 404, 500.
- Toda lógica principal deve estar dentro de `try-catch`. Logar com `error_log("[CONTEXTO] Erro: " . $e->getMessage())`.
- Conexão DB sempre via `new Database()` + `$db->getConnection()`. Services recebem a conexão no construtor.
- **Auditoria obrigatória** em toda operação de escrita (INSERT/UPDATE/DELETE) em tabelas críticas via `AuditoriaService->registrar()`.
- Tentativas de login (sucesso/falha) registradas via `AuditoriaService->registrarLogin()`.
- Nunca usar `var_dump` ou `print_r` em produção; usar `error_log()` com prefixos claros (ex: `[TICKETS POST]`).
- Configurações sensíveis via `Environment::get('key')`.

### Frontend Moderno (FRONTEND_MODERNO.md)
- **Tipografia obrigatória: Inter** (Google Fonts).
- Usar variáveis CSS definidas em `modern-enhancements.css`: `--brand-500`, `--text-secondary`, `--bg-card`, `--shadow-sm`, `--shadow-md`, `--radius-sm`, `--radius-md`, `--transition-fast`.
- Compatibilidade obrigatória com **modo escuro**.
- Interatividade: ripple effect, hover states, transições suaves.
- **Proibido**: Arial/Times/Comic Sans; roxo/violeta; elementos desalinhados; animações pesadas.
- Cards: `--shadow-sm`/`--shadow-md`, `--radius-lg`. Modais: backdrop blur + animação scale/fade-in.
- **Vanilla JS puro e modular**. Não adicionar React/Angular/Vue ao core existente.
- Sempre tratar erros de fetch com notificações visuais (Toasts/Alerts).

### Segurança (SEGURANCA_SPEC.md)
- **Sempre** usar Prepared Statements PDO. **Nunca** concatenar strings em queries SQL.
- Validar tipo de arquivo por conteúdo (finfo/MIME), não apenas extensão. Usar `basename()` em caminhos.
- Senhas sempre com `password_hash($senha, PASSWORD_ARGON2ID)` e `password_verify()`.
- Headers de segurança obrigatórios: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `X-XSS-Protection`, `Referrer-Policy`, `Content-Security-Policy`.
- Sessões PHP com `secure`, `httponly`, `samesite: Strict`. Regenerar ID após login.
- Rate limiting em login. CSRF token em formulários (`bin2hex(random_bytes(32))`).
- Permissões de arquivo: PHP `644`, diretórios `755`, config `600`. **Nunca** `777` em produção.
- Nunca expor `.env`, `.git`, `composer.json` publicamente.
- **Nunca logar**: senhas, tokens de sessão, dados pessoais sensíveis.

### Acessibilidade WCAG 2.2 (ACESSIBILIDADE_SPEC.md)
- HTML semântico obrigatório: `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<footer>`. Nunca `<div class="header">`.
- Contraste mínimo: texto normal 4.5:1, texto grande 3:1, componentes UI 3:1.
- Formulários: `<label for>` associado a todo `<input>`. Mensagens de erro com `role="alert"` e `aria-live="polite"`.
- Foco visível obrigatório: `outline: 2px solid` em `button:focus`, `a:focus`, `input:focus`. **Nunca** remover outline sem substituto.
- Imagens com `alt` descritivo. Ícones decorativos: `aria-hidden="true"` + `.sr-only` para leitores de tela.
- Modais com `role="dialog"`, `aria-modal="true"`, `aria-labelledby`. Gerenciar foco ao abrir/fechar. Fechar com ESC.
- Tabelas com `<caption>`, `<thead>`, `<th scope="col">`.
- Mensagens de status: `role="status" aria-live="polite"`. Alertas urgentes: `role="alert" aria-live="assertive"`.
- Animações respeitam `@media (prefers-reduced-motion: reduce)`.
- `<html lang="pt-BR">` obrigatório.

### Acesso ao Banco de Dados Local (DB_ACCESS_LOCAL.md)
- Executável MySQL: `C:\Program Files\MySQL\MySQL Server 8.4\bin\mysql.exe` (o MySQL do XAMPP não é o usado).
- Conexão: host `localhost`, database `db_conecta`; usuário e senha em `api/config/.env` (`DB_*_LOCAL`).
- Comando padrão: `"C:\Program Files\MySQL\MySQL Server 8.4\bin\mysql.exe" -u root -p -e "USE db_conecta; SUA_QUERY_AQUI;"`
- Os dumps em `database/` são **estáticos e podem estar desatualizados**. Usar o MySQL em execução como fonte da verdade.
- Dump atualizado: `"C:\Program Files\MySQL\MySQL Server 8.4\bin\mysqldump.exe" -u root -p db_conecta > db_conecta_atual.sql` (fora do repositório).
- UPDATE/DELETE com **EXTREMA CAUTELA**: sempre com `WHERE id = ?`. Scripts temporários de manutenção devem ser removidos após uso.
